04

Behavioral changes

Highest risk

These three are code I changed rather than deleted, and none of them is covered by the automated suite. If you only have time for one phase, make it this one.

Read before check 15

/restart spawns a new PID, so the hook dies with the old process. Restart detection scans _outputBuffer, which the dead hook no longer fills — so it will time out at 30s, log Restart completion not detected via logs within timeout, proceeding with PID detection anyway, then continue via PID diffing.

This is not a regression. The old code also always timed out in hook mode, because _lastLogFilePosition never advanced when log monitoring wasn't running. The timeout is non-fatal.

⚠

Regression watch list

Not numbered — these aren't steps. They're the things most likely to bite that don't look in scope.

  • GET /api/server/logfile still works. WreckfestWeb's log viewer depends on it, and it survived the log-file removal on purpose.
  • Webhooks server-started, server-stopped, server-restarted and server-attached all still fire.
  • SmartRestartService countdown messages use the same /message dispatch path as voting — but fire unattended during a scheduled event.
  • Multi-instance deserves one pass with two servers running. The old ConsoleWriter.FindConsoleWindow() grabbed any console window; the hook is per-process by pipe name, so this should now be correct where it previously wasn't.

Suggested order. Phases 1–3 give you confidence in about an hour without a populated server. Phase 4 deserves the most attention — those changes are unproven live. Phase 6 needs real players. Ticks are saved in this browser only.
